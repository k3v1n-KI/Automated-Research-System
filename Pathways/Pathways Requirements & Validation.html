01

Purpose & scope

Pathways is a service-search and directory-maintenance tool for healthcare navigators — the nurses, social workers, and community health workers who spend their days connecting patients to social and health services. In a region like the Algoma OHT, finding the right service today means juggling stale PDF directories, spreadsheets, and group texts. Pathways replaces that with a single search box backed by a directory that the navigators themselves keep alive.

This document specifies what must be built to turn the existing high-fidelity prototype (a click-through React mock) into a functional system capable of running a research evaluation. It is written for two readers at once:

  • The implementing developer — who needs functional and non-functional requirements, a data model, an architecture, and a test plan precise enough to build from.
  • The paper author — who needs an evaluation methodology that yields defensible quantitative results without recruiting human participants.
Scope of the build

A research-grade MVP of the core loop — Find → Verify → Ask → Close — with real persistence, a real natural-language pipeline, and an instrumented ranking engine. Production concerns (SSO with provincial identity providers, full moderation tooling, mobile apps) are documented as COULD but are out of scope for the evaluation.

What the prototype already establishes

The prototype is the functional specification of the UX. Where this document and the prototype disagree, the prototype wins on interaction and layout; this document wins on what happens on the server, how the AI behaves, and how we measure it. The prototype currently fakes three things that the real system must implement for real:

  • Natural-language extraction — the prototype uses regular expressions to turn a typed sentence into filter chips. The real system uses an LLM-based extractor (§7).
  • Ranking — results are hard-coded in a fixed order. The real system computes a fit + freshness − flag score (§7).
  • The flywheel — confirms, flags, Asks, and case-closes mutate in-memory React state and vanish on refresh. The real system persists every event as an immutable chain of custody (§5).

Problem, users & the core loop

One loop keeps a directory alive.

The users

Contributing navigator The same person in a different mode — confirming, flagging, answering Asks, closing cases. Keep the directory accurate with near-zero extra effort, as a by-product of doing their job.

A note on patient data

Navigators search by structured needs, never patient identifiers ("same-day MH walk-in, adolescent, no OHIP, Sault Ste. Marie"). The system is designed so that no personal health information (PHI) is required to operate it — a deliberate privacy posture that also simplifies the research ethics story (§4, §9).

The core loop

Pathways is a single flywheel. Every pass a navigator makes through it leaves the shared directory more accurate than they found it — which is the central claim the research must validate.

Data model

An append-only spine.

The central design decision: a resource's current state is not stored as mutable rows — it is derived from an append-only stream of verification events. This is what makes the chain of custody trustworthy and the flywheel measurable. Core entities:

Caseid, owner_id, title, summary, extracted_filters, status, regionThe navigator's private working record. Filters are the structured extraction.
Referralid, case_id, resource_id?, free_text?, outcome, note, created_atOn close. A free-text referral with no resource_id spawns a candidate Resource.

Why event-sourced

Three payoffs: (1) the chain of custody is free and tamper-evident; (2) freshness is just now − latest confirm event, computed not stored; (3) the flywheel simulation can replay or inject events through the same write path the UI uses — so the thing you measure is the thing you built.

6.1  Request flow — a search

  1. SPA sends the raw sentence to the Search service.
  2. Search service calls the Extractor (LLM) → structured filters; returns them immediately so chips render while ranking runs.
  3. Filters drive retrieval against the search index (candidate set, e.g. top 100 by BM25 + vector similarity).
  4. The Ranking engine scores each candidate by fit + freshness − flags (§7.2) and returns the ordered list.
  5. Everything is written to SearchLog (FR-F8 / NFR-I1).

6.2  The AI approach (hybrid)

Recommended default is a hybrid: an LLM does the linguistically hard part (turning messy natural language into a typed filter object), while classic information-retrieval ranking (BM25 / vector retrieval + a transparent scoring formula) does the part that must be fast, explainable, and cheap to run thousands of times in simulation. This keeps the ranking auditable — essential for the paper — and avoids burning an LLM call per candidate.

The extractor can be a hosted LLM API or a self-hosted open model; either way it sits behind a single extract(text) → Filters interface so it is swappable and mockable in tests.

07

Key feature: NL search + freshness-weighted ranking

The claim the paper rests on.

This is the feature the evaluation targets. It has two halves that are tested separately (§9): an extractor (language → structured filters) and a ranker (filters + a living index → an ordered, trustworthy list).

7.1  Extraction schema

The extractor maps a free-text sentence to a typed Filters object. This schema is also the gold-label format for the extraction benchmark (Study 1).

// extract("Same-day MH walk-in for an adolescent, no OHIP, Sault Ste. Marie")
{
  need:        ["mental-health"],        // service domain(s)
  modality:    ["walk-in", "same-day"], // how care is delivered
  population:  ["adolescent"],          // age / group
  coverage:    ["no-OHIP"],             // funding / eligibility
  location:    "Sault Ste. Marie",       // region / community
  language:    [],                       // e.g. "fr", "ojibwe"
  urgency:     "same-day",
  confidence:  { need: 0.97, location: 0.92, ... }
}

Low-confidence fields are shown as suggested chips the navigator can confirm or drop (FR-F2/F6), which both improves trust and yields a free correction signal.

7.2  Ranking score

Each candidate resource r for query filters q gets a transparent, tunable score. The freshness term is the novel part — it makes the directory's self-maintenance visible in the ranking itself.

score(r, q)  =  wf·Fit(r,q) + wv·Fresh(r) − ws·Flag(r)

Fit — semantic + filter match, 0..1 (BM25 ⊕ vector ⊕ filter overlap)
Fresh — index over fields used by q:
  Fresh(r) = meani∈q [ exp( − age(fieldi) / τ ) · g(confirmsi) ]
Flag — fraction of q-relevant fields currently flagged-stale, 0..1

τ = freshness half-life (config, e.g. 60d) · g(·) = saturating confirm-count weight
defaults: w_f = 0.6, w_v = 0.3, w_s = 0.4

The weights (w_f, w_v, w_s) and half-life τ are configuration, not constants — the ablation in Study 2 sweeps them. Setting w_v = w_s = 0 recovers a pure fit ranking, which is exactly the baseline the freshness mechanism is measured against.

Design property to preserve

Freshness is computed only over the fields the query actually depends on — a clinic with stale accessibility info isn't penalised on a query that never asked about accessibility. This makes freshness query-relative and is worth stating explicitly in the paper.

8.2  Integration tests

  • Search pipeline: real extractor (or a pinned fixture model) → retrieval → ranking → SearchLog written. Assert ordering and that logging is complete.
  • Verification round-trip: confirm/flag via API → event appended → field state + ranking weight change on the next search.

Drive the whole loop through the UI, mirroring the prototype's demo script: Find (dictate → search) → Verify (confirm Hours, flag Referral) → Ask (post, see reply) → Close (refer, seed, resolve). Run on Chromium + WebKit; include a keyboard-only pass and an axe-core accessibility scan.

09

Validation & evaluation methodology

Quantitative evidence — no human subjects.

The constraint shapes everything here: we will not test with real people, yet we need numbers a paper can stand on. The strategy is to evaluate the key feature on three fronts that together cover its claims, each producing reportable metrics with confidence intervals. The first two are standard information-retrieval evaluations on a labelled corpus; the third — the centrepiece — is an agent-based simulation of the flywheel driven through the real system API (NFR-I2).

Study 1
Extraction accuracy — language → filters. Metrics: precision / recall / F1.
Study 2
Ranking quality — fit + freshness vs. baselines. Metrics: nDCG, MRR, P@k.
Study 3
Flywheel simulation — index accuracy & freshness over time. The core contribution.

9.1  Building the evaluation corpus

All three studies need a labelled dataset, built once with no live participants:

  • Case vignettes (queries). Author 150–300 case sentences spanning the need / population / coverage / location / language space. Seed them from the prototype's realistic Algoma examples, then expand by combination. Optionally use an LLM to paraphrase each into 2–3 surface forms to test robustness — but the gold labels are written/checked by hand.
  • Gold filters. For each vignette, the correct Filters object (§7.1) — this is the answer key for Study 1.
  • Resource corpus + ground truth. A synthetic-but-realistic directory of ~200–500 Algoma-style services with full fields. Crucially, define a ground-truth value for every field so the simulation can know when the stored value is right or wrong.
  • Relevance judgments. For each query, graded relevance (0–3) of resources — for Study 2's nDCG. Generate candidate judgments by rule + LLM, then have 1–2 domain reviewers adjudicate a sample to establish inter-rater reliability (report Cohen's κ). This is expert review of data, not human-subjects testing.

Study 3Agent-based simulation of the flywheelRQ3 · RQ4 — core contribution

This is what makes "the directory maintains itself" a measurable claim rather than a slogan. We model a population of synthetic navigators acting on the real system over simulated time, and watch whether the index stays accurate.

The model

  • World. The resource corpus, each field with a hidden ground-truth value and a stored value + last-verified time.
  • Drift. Each field's ground truth changes as a Poisson process at rate λ_change (hours change, programs close). On change, the stored value silently becomes wrong until someone corrects it — this is the decay a static directory suffers.
  • Agents. P navigators. Each timestep an agent issues searches drawn from the query distribution, opens top-k results, and — modelling real behaviour — with probability p_confirm confirms a field it relied on, and with probability p_flag flags a field it discovers is wrong. A flag triggers a correction after delay d.
  • Coverage. A fraction of searches that fail spawn an Ask; some Asks seed a new candidate resource — modelling growth (FR-C3/K2).
  • Driven through the real API. Agents call the same confirm/flag/seed/search endpoints the UI calls (NFR-I2), against a seedable clock. The simulation exercises production code.

Outcome metrics (over simulated time t)

MetricDefinition
Index accuracy A(t)Fraction of fields where stored value = ground truth.
Freshness F(t)Fraction of fields verified within window W.
Usage-weighted accuracyA(t) weighted by how often each resource is actually returned — popular resources should stay fresher. (Key hypothesis.)
MTTCMean time-to-correction: from a fact changing to its stored value being fixed.
Coverage C(t)Resources / fields present in the index over time (growth via seeding).
Effective search accuracyAccuracy of the fields actually shown to agents in their top-k results — the number a navigator experiences.

Conditions & sweeps

  • Baseline: static directory — no verification (stored never updates). A(t) decays monotonically; this is the "old PDF" world.
  • Pathways: the full loop. Hypothesis: A(t) reaches and holds a steady state well above baseline.
  • Parameter sweep: population P (5 → 100), participation p_confirm / p_flag (e.g. 0.02 → 0.3), drift rate λ_change, correction delay d. Find the minimum participation at which the index self-sustains — a headline result.
Replication
Monte Carlo: ≥ 100 runs per cell with different seeds; report mean ± 95% CI (and shaded bands on time-series plots).
Stats
Compare steady-state A and MTTC across conditions (Mann–Whitney / t-test as appropriate); regression of steady-state accuracy on P and participation to expose the scaling law.
Calibration
Parameter ranges grounded in literature on directory decay / link rot and stated explicitly as assumptions; sensitivity analysis shows which assumptions matter.
Study 4LLM-as-simulated-navigator (optional, strengthening)supports RQ1–RQ3

To make the synthetic query stream more realistic than hand-written vignettes, drive a subset of agents with an LLM prompted as navigator personas: given a generated patient scenario, it writes the search sentence and decides whether to confirm/flag what it's shown. This produces a richer, less hand-tuned query distribution for Studies 1–3 and a qualitative error analysis of where extraction breaks. Use as a supplement, not the sole evidence — and disclose it plainly, since LLM-simulated users are not human users.

Threats to validity — state these in the paper

Construct: simulated navigators are a model of behaviour, not real clinicians — calibrate parameters and run sensitivity analysis. Internal: the query corpus is partly author-generated; mitigate with expert-adjudicated relevance and inter-rater κ. External: one synthetic region; generalisation to other OHTs is argued, not measured. Honest framing: this is a systems + simulation evaluation that establishes feasibility and the self-maintenance mechanism — a human field study is named explicitly as future work.

H2Freshness-weighted ranking yields higher nDCG@10 and lower stale-result-rate@10 than fit-only ranking, and the advantage grows as the index ages.
H3Under the flywheel, steady-state index accuracy strictly dominates the static baseline, and usage-weighted accuracy exceeds overall accuracy (popular resources stay fresher).
H4MTTC decreases monotonically with population and participation rate; there exists a participation threshold above which accuracy self-sustains above a target (e.g. 0.9).
